# Application Atlas change boundaries

- Keep each change within the area the user asks to edit. For a style or motion request, edit presentation, decorative markup, and animation code only. Leave planner logic, source data, privacy, and deployment configuration alone unless the user also asks to change them.
- Preserve the working roadmap and filters, browser-saved progress and school edits, achievements, official source links, and RFEG handicap display and update path. Keep existing content, section anchors, storage keys, and data formats stable for visual changes.
- Build on existing visual features. Preserve the Three.js orbital scene and its static fallback, pointer-responsive artwork, progress meter animations, color pulse, and responsive layout unless the requested change specifically replaces one.
- Keep motion decorative. Text and controls should stay readable and usable while scrolling. Respect reduced motion and keep decorative layers out of keyboard and pointer interaction.
- Review the diff for unrelated edits. Before a visual release, check desktop, mobile, reduced motion, and at least one affected workflow. Use the existing deployment and publish only the built public assets.
